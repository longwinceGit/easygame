## 1. Problem Statement（问题陈述）

**我们在解决什么问题？**

项目已有一个成熟的 Android 模板工程（MVVM + Repository + Room + Navigation + Material 3），但里面的笔记 Demo 只是架构演示，没有任何面向真实用户的业务。用户需要一个**能被真实玩家玩起来的游戏 App**，并且明确要求：

1. 第一款游戏是**可拖拽的俄罗斯方块**（非传统的左右/旋转按钮操作）；
2. **后续要能持续接入多款游戏**——这是硬约束，不是"以后再说"。

**如果不解决的代价**：每加一款游戏就重写一遍壳（生命周期、计分、存档、返回栈、主题），第 3 款游戏的边际成本不会下降，最终退化为多个互不相通的独立 App。

**Evidence（证据）:**

| 类型 | 内容 | 说明 |
|------|------|------|
| 干系人陈述 | "当前只有一款游戏……后续可以增加多款游戏" | 一手需求，明确的多游戏扩展意图 |
| 现有资产 | 模板工程已具备 Room / Navigation / M3 设计令牌 / 双主题 | 壳层基础设施已就位，缺少的是游戏插件层 |
| 技术风险 | Android 游戏常犯错误：逻辑与 View 强耦合 | 一旦耦合，每款游戏都要重写渲染与状态机 |

> ⚠️ **诚实的证据声明**：本 PRD 没有用户访谈、没有行为数据、没有客服信号。这是一个由干系人直接给出的**方向性需求**，不是从用户研究中浮现的问题。本 PRD 中以「假设」标注所有未经度量的判断，并在第 5 节给出验证方式。我不会把猜测伪装成数据。

## 2. Goals & Success Metrics（目标与成功指标）

| Goal | Metric | Baseline | Target | 度量窗口 |
|------|--------|----------|--------|----------|
| G1 · 壳可扩展 | 新增一款同等复杂度游戏的接入工时 | 无（首次） | **≤ 1 人日**，且不修改壳层任何文件 | 第 2 款游戏上线时 |
| G2 · 核心玩法可玩 | 完成一局（放置 ≥ 20 个方块）的用户占比 | 无 | ≥ 70% | 内测阶段 |
| G3 · 拖拽手感 | 拖拽放置成功率（松手后成功落子 / 总拖拽次数） | 无 | ≥ 90% | 内测阶段 |
| G4 · 稳定性 | 崩溃率 / 卡顿（单帧 > 32ms 占比） | 无 | < 0.5% / < 2% | 内测阶段 |
| G5 · 成绩留存 | 关闭 App 后重进，最高分仍正确 | 无 | 100% | 内测阶段 |

**北极星指标**：单用户日均游戏局数（Engagement）——它同时反映"壳够好用"和"游戏够好玩"。V1 只建立埋点口径，不设定目标值（无基线）。

## 3. Non-Goals（本次明确不做）

| 不做的事 | 原因 | 重新考虑的条件 |
|---------|------|--------------|
| 在线排行榜 / 账号系统 / 云存档 | V1 无后端，Room 本地存档已满足 G5 | 有后端服务且 DAU > 1000 |
| 第二款及以后的游戏本体 | 本迭代只交付**接口与注册机制**，不交付第二款内容 | 壳验证完成（G1 达标） |
| 内购 / 广告 / 变现 | 无合规与支付基础设施 | 明确的商业化决策 |
| 音效与背景音乐资源 | 需素材版权，MVP 阶段用触觉反馈（Haptic）替代 | 素材到位 |
| 自动下落（重力）/ 限时模式 | 与"拖拽"的核心定位冲突，会让玩家失去掌控感 | 用户明确要求"经典模式" |
| 手柄 / 键盘 / 平板分屏适配 | 手机竖屏为唯一目标形态 | 有明确的平板需求信号 |
| 多语言（i18n） | 仅中文 | 出海需求 |

## 4. User Personas & Stories（用户画像与故事）

**Primary Persona：小林，26 岁，通勤族**
地铁/排队时用手机打发 3–10 分钟。想要"随时拿起、随时放下、不用学"的游戏。讨厌开局教学、讨厌误触、讨厌被倒计时逼着走。

**Secondary Persona：开发者（本项目后续维护者）**
要在不改动壳层代码的前提下接入新游戏，希望有清晰的接口和一份照着抄就能跑的示例。

### Story 1 — 拖拽放置
> 作为小林，我想要**用手指把方块拖到棋盘上松手即落**，以便不用在小小的按钮上戳来戳去。

- [ ] Given 拖拽开始时，when 手指在棋盘上方移动，then 棋盘实时显示该方块的**落点预览**（幽灵块），并高亮所在列
- [ ] Given 落点合法，when 松手，then 方块硬降落至该列最底可落位置，落点预览为品牌色
- [ ] Given 落点非法（该列已满），when 手指悬停，then 预览变红且不显示落点；when 松手，then 方块**回到托盘**，不消耗、不扣分
- [ ] Given 手指从未离开托盘区域（视为点击），when 松手，then 执行**旋转 90°**而非放置
- [ ] Performance: 拖拽过程 60fps，单帧渲染 < 8ms

### Story 2 — 消行与计分
> 作为小林，我想要看到消行和分数上涨，以便判断自己玩得好不好。

- [ ] Given 放置后存在满行，when 判定完成，then 该行消除、上方行整体下移，并播放 ≤ 200ms 的闪烁反馈
- [ ] Given 一次消除 n 行，when 计分，then 得分 = 基础分(n) × 等级 + 连击奖励
- [ ] Given 连续放置都消行，when 计分，then 连击数累加并给出额外奖励

### Story 3 — 结束与存档
> 作为小林，我想要在死后看到本局分数和历史最高分，以便有再来一局的动机。

- [ ] Given 托盘中剩余方块在**所有列 × 所有旋转**下均无法放置，when 判定完成，then 游戏结束并弹出结算卡片
- [ ] Given 游戏结束，when 存档，then 写入 Room，退出 App 后重进仍可读到最高分
- [ ] Given 结算卡片，when 点击"再来一局"，then 棋盘清空、分数归零、状态回到 RUNNING

### Story 4 — 游戏大厅（壳）
> 作为小林，我想要在一个列表里看到有哪些游戏可以玩，以便直接点进去。

- [ ] Given 大厅已加载，when 查看，then 展示所有已注册游戏（V1 仅 1 款），含名称、图标、简介、主题色
- [ ] Given 点击某款游戏卡片，when 跳转，then 进入该游戏页面，返回键可回到大厅

### Story 5 — 开发者接入（验收 G1）
> 作为开发者，我想要只新增文件、不改壳层代码就能上架一款新游戏。

- [ ] Given 已实现 `GamePlugin` 与对应 Fragment，when 在 Registry 中注册一行，then 大厅自动出现该游戏
- [ ] Given 新增游戏，when 检查 diff，then 壳层文件（Hub / Registry / MainActivity / nav_graph 根）改动 ≤ 1 行注册代码

## 5. Solution Overview（方案概述）

一个 **Game Hub 壳 + 插件式游戏层** 的 Android App。壳负责：大厅列表、导航、主题、存档、成绩；每款游戏是一个自包含的插件包（`game/<gameId>/`），实现统一接口后注册进 `GameRegistry`，大厅自动发现。

第一款游戏 **拖拽方块（Drag Tetris）** 采用**无重力的策略放置玩法**：托盘常驻 3 个待放方块，玩家拖拽任意一个到棋盘任意列，松手即硬降落；三个都用完后自动补充新的三个；当托盘里剩下的方块**全部无处可放**时游戏结束。经典的"满行消除 → 上方下移"规则保留。

**Key Design Decisions:**

| 决策 | 选择 | 放弃的东西 |
|------|------|-----------|
| D1 · 操作范式 | **纯拖拽放置，无自动下落** | 放弃经典俄罗斯方块的时间压力与手速考验。理由：与"可拖拽"的需求直接一致，且通勤场景下可随时中断 |
| D2 · 垂直拖拽语义 | **垂直位置决定"进入高度"，再从该高度向下重力吸附到不能再落**（v1.1 修订） | 放弃"必须能从棋盘顶部一路畅通"。理由：原方案下玩家无法把方块递进被上方遮挡的空腔，实测为最影响可玩性的问题；仍保留重力吸附，维持"总会落到不能再落"的直觉 |
| D3 · 旋转时机 | **托盘内点击旋转，拖拽中不旋转** | 放弃拖拽中旋转。理由：单指拖拽时无法可靠接收第二次点击，双指手势学习成本高、误触率高 |
| D4 · 渲染方式 | **自定义 View + Canvas 硬绘** | 放弃 View 逐格堆叠（200 个 View 会拖垮帧率）、放弃 OpenGL/游戏引擎（引入过重依赖，与"轻量模板"定位冲突） |
| D5 · 逻辑分层 | **引擎层为纯 Java，零 Android 依赖** | 多一点胶水代码。理由：引擎可被 JVM 单测直接覆盖，且换渲染层（Compose/引擎）时逻辑不动 |
| D6 · 存档 | **Room 保存每局记录 + 聚合最高分** | 放弃 SharedPreferences。理由：模板已有 Room 基础设施，且未来要做"最近对局列表" |
| D7 · 第二款游戏 | **只交付接口与注册机制，不交付内容** | 延期到 V1.1。理由：先用真实游戏验证抽象是否成立，再抽象第二次 |

## 6. Technical Considerations（技术考量）

**Dependencies:**
| 依赖 | 用途 | Owner | 风险 |
|------|------|-------|------|
| 模板现有 Room / Navigation / M3 | 壳层基础设施 | Eng | Low（已在用） |
| `androidx.recyclerview` | 大厅列表 | Eng | Low |
| 无第三方游戏引擎 | — | — | Low |

**Known Risks:**
| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|-----------|
| 拖拽手势与点击旋转冲突（误判） | Medium | Medium | 8dp 位移阈值 + 时间阈值判定；提供"撤销上一次放置"作为兜底？——**V1 不做撤销**，改为非法放置直接回弹（零惩罚） |
| 小屏设备上棋盘过小（cell < 16dp） | Medium | Medium | 棋盘按高度自适应，cell 下限 14dp；低于阈值时缩减可见行数 |
| 抽象过度：为一款游戏设计了复杂插件层却用不上 | Medium | High | 插件接口**只保留 5 个方法**（见架构文档），且必须被第一款游戏真实使用，不预留"未来可能用到"的空方法 |
| 抽象不足：第二款游戏接入时发现接口不够 | Medium | Medium | 接口只定义"壳需要知道的最小元信息"，游戏内部完全自治，扩展点天然充足 |
| 模板笔记 Demo 与新游戏共存造成导航混乱 | Low | Low | 直接移除笔记 Demo（模板 README 已声明 Demo 可被替换） |

**Open Questions（开发前必须解决）:**
- [x] 是否需要撤销功能？→ **否**。非法放置零惩罚回弹，已足够容错。
- [x] 是否保留底部导航？→ **保留**，改为「游戏」/「战绩」两个 Tab，既保留模板架构特征又符合游戏 App 信息架构。
- [ ] 单局时长目标是多少？→ 无数据，V1 不设目标，仅埋点。**Owner: PM，Deadline: 内测结束后**

## 📌 交接给「游戏设计师」的输入

1. 已锁定范围：**无重力拖拽放置**的俄罗斯方块，10×20 棋盘，托盘 3 格，满行消除，无处可放则结束。
2. 已锁定的交互红线：拖拽中不旋转、垂直拖拽不改变落点、非法放置零惩罚回弹。
3. 需要你产出：核心循环、方块集合与生成算法、计分/连击/等级公式、难度曲线、失败条件的精确判定、以及**玩家第一次打开时的 15 秒上手路径**。
4. ⚠️ 已删除的旧约束：原"垂直拖拽位置不参与落点计算"在实测中被证明会造成"方块放不进下方空腔"，已由 GDD v1.1 修订为"手指决定进入高度 + 重力吸附"。
4. 约束：手机竖屏单手操作，单局目标时长 3–10 分钟（待验证）。
