## 0. 一句话（先写新闻稿，再写 PRD）

> 手机里又多了一款"等电梯时能开一把、卡住时甘心重来一次"的解谜游戏：
> 停车场被塞满了，彩色巴士要接走上方排队的小人，可去路被横向停着的障碍车堵死。
> 你点一辆车，它只肯顺着车头箭头一路开到底——所以得先把挡路的挪开。
> 更麻烦的是上方的接客位只有 3 个，派错颜色的车上去会白占一格。
> **不用联网、没有广告、没有倒计时，卡住了就撤销一步重想。**

## 1. Problem Statement（问题陈述）

**我们解决什么痛点**

现有工程 `easygame` 是一个 Android 游戏合集壳，只装了一款《拖拽方块》。
它面临两个具体问题：

1. **内容单薄**：壳里只有一款游戏，"合集"这个定位名不副实，用户打开后没有第二个可去的地方。
2. **架构承诺未被验证**：`docs/03-architecture.md` 与 ADR-001 声称"新增游戏只改壳层 1 行"，
   但这条承诺**只有一款游戏时无法被证伪**——真实验证必须发生在第二款游戏接入的那一刻。

**不解决这两个问题的代价**

- 用户侧：合集无内容可消费，留存没有第二个抓手。
- 工程侧：ADR-001 是个未被检验的假设。若第二款游戏接入时被迫修改壳层，
  说明插件抽象是错的，越晚发现返工越大。

**Evidence（证据）**

- User research（用户研究）：**无**。本项目没有任何用户访谈、问卷或可用性测试。
- Behavioral data（行为数据）：**无**。工程未引入任何埋点/统计（`README.md` 已声明），
  因此没有"用户玩了几局""在哪流失"这类数据。
- Support signal（客服信号）：**无**。未上架，无用户反馈渠道。
- Competitive signal（竞争信号）：**有，但为二手观察**。
  "挪车消消消 / 巴士迷阵 / 停车场挪挪车"一类玩法在国内小程序与短视频广告中高频出现，
  说明该品类存在规模化投放验证过的需求；同一玩法被反复"换皮"投放，
  是品类需求被验证的强信号，也是玩法同质化的警钟（见 §3 Non-Goals）。

> **诚实声明**：本 PRD 的优先级判断建立在"竞品二手观察 + 工程架构诉求"之上，
> **不是**建立在一手用户证据之上。所有目标值都是方向性假设，上线后需要用真实行为数据回校。

## 3. Non-Goals（本次明确不做的事）

| # | 不做 | 原因 |
|---|------|------|
| 1 | **不做广告变现** | 工程未声明 `INTERNET` 权限、未接入任何广告 SDK。原品类游戏靠"看广告加接客位/加道具"变现，本作**直接删掉该变现点** |
| 2 | **不做内购与货币** | 无支付渠道、无账号体系。原玩法的"金币 P10"不移植 |
| 3 | **不做"排序"道具**（重排乘客队列） | 它会把解谜压力直接归零，与"规划顺序"这一核心乐趣正面冲突。保留顺序张力，用**无限撤销**替代它来兜底试错成本 |
| 4 | **不做"看广告扩充接客位"** | 接客位固定 3 个。这是核心难度旋钮，不能变成付费旋钮 |
| 5 | **不做埋点 / 崩溃上报 / 云存档 / 排行榜** | 与工程"无网络、无追踪"的定位一致。代价是 G3–G5 当前不可度量，接受 |
| 6 | **不做关卡手工设计与存档** | 关卡由生成器按关卡号随机产出。手工关卡是内容运营项目，不是本次范围 |
| 7 | **不做横屏 / 平板布局** | 沿用壳层 `screenOrientation="portrait"` |
| 8 | **不做音效与音乐** | 无音频资源、无音频引擎依赖 |
| 9 | **不修改《拖拽方块》** | 本次是新增模块，俄罗斯方块的代码、文档、数值一律不动 |

## 4. User Personas & Stories

**Primary Persona：碎片时间玩家「小林」**
通勤/排队时拿出手机，期望 2–5 分钟内获得一次完整的"想明白—做对了"的正反馈，
不想被倒计时催、不想被弹窗打断、不想为了一次失误付出重开的代价。

---

**Story 1**：作为玩家，我点一辆车，它沿着车头箭头一路开到底，让我能预判结果。
- [ ] Given 停车场中一辆朝上的红色巴士上方无阻挡，when 我点击它，then 它开到顶部并驶出停车场
- [ ] Given 一辆朝上的车上方被障碍车挡住，when 我点击它，then 它前进到紧贴障碍车的位置停下
- [ ] Given 一辆横向障碍车，when 我点击它，then 它沿箭头方向滑到不能再滑为止
- [ ] Given 一辆车在箭头反方向有空间，when 我从车上沿反方向拖动，then 它移动到我松手的位置（可停在中间）
- [ ] Performance：从 `ACTION_UP` 到界面完成重绘 ≤ 1 帧（16ms），滑动动画 180ms

**Story 2**：作为玩家，我能通过挪开障碍车，为指定颜色的车让出向上的通道。
- [ ] Given 红色巴士上方有横向障碍车，when 我先把障碍车挪到别的列，then 红色巴士可以驶出
- [ ] Given 我连续操作后局面变差，when 我点「撤销」，then 局面回到上一步之前
- [ ] Given 我撤销到底，when 再次点「撤销」，then 按钮禁用且不崩溃

**Story 3**：作为玩家，我理解"接客位只有 3 个"带来的顺序压力。
- [ ] Given 队首是蓝色乘客，when 一辆红色车驶出，then 红色车占用一个接客位（不接客）
- [ ] Given 接客位已停着红色车，when 蓝色乘客被接完后队首变成红色，then 红色车自动接客驶离，车位释放
- [ ] Given 3 个接客位全满且无车匹配队首，when 一辆无法接客的车试图驶出，then **它开不出去**（停在顶部），并提示"接客区已满"
- [ ] Given 队首乘客被接走，when 队列前进，then 上方乘客队列可视化同步更新

**Story 4**：作为玩家，卡住时有低成本的补救手段，不必重开整个进度。
- [ ] Given 局面仍有可动车辆，when 我点「刷新」，then 当前关卡重新随机生成（关卡号不变，本关进度清零）
- [ ] Given 我点「移除」，when 我再点一辆灰色障碍车，then 该障碍车消失；每关限 1 次
- [ ] Given 本关「移除」已用完，when 我再次点「移除」，then 按钮禁用
- [ ] Given 停车场中已无任何车辆可移动，when 判定发生后，then 弹出"卡住了"对话框，提供 撤销 / 刷新 / 返回大厅

**Story 5**（验收 G1，开发者视角）：作为开发者，我接入这款游戏时不需要改壳层逻辑。
- [ ] Given 我要新增一款游戏，when 我照 `docs/07-dev-guide.md` 操作，then 我只新增 `game/parking/` 下的文件，并在 `GameRegistry` 静态块加 1 行
- [ ] Given 壳层代码，when 我搜索 `import com.template.app.game.parking`，then **唯一命中是 `GameRegistry.java`**（白名单）
- [ ] Given 领域层代码，when 我搜索 `import android.`，then **零命中**
- [ ] Given 停车场为空，when 我打开大厅，then 新游戏出现在卡片列表中，可点击进入、可返回

## 5. Solution Overview（方案概述）

**结构**：在现有插件壳内新增第二个自包含游戏包 `com.template.app.game.parking`，
与 `game.tetris` 平级、互不依赖。大厅自动出现第二张卡片——壳层唯一改动是
`GameRegistry` 静态块中多一行 `register(new ParkingGamePlugin())`。

**核心玩法（三层）**

1. **空间层（华容道）**：8×8 停车场。彩色车四向箭头，可接客；
   灰色障碍车一律横向、箭头左/右，纯阻挡。点一辆车，它沿箭头滑到底。
   玩家的决策是"以什么顺序点"，以及"用拖动精确停位"。
2. **顺序层（颜色匹配）**：上方乘客按颜色排队，**只服务队首**。
   颜色匹配的驶出车直接接客离开；不匹配的驶入接客区占一个车位（共 3 个）。
   等队首轮到它的颜色时，停着的车自动接客驶离、车位释放。
3. **压力层（容量约束）**：3 个接客位是唯一的失败旋钮。
   塞满且无车匹配队首时，任何车都开不出去——玩家必须靠撤销/移除自救。

**为什么"只能服务队首"**：这是本作全部难度与规划乐趣的来源。
若允许任意颜色插队，接客位约束立即失效（总能找到匹配车），游戏退化成纯华容道。
代价是"派错车"会真地堵死自己——因此必须配套**无限撤销**（见 §3 Non-Goals 第 3 条）。

**可解性保证**：关卡不是随机丢车然后祈祷能解，而是**先随机布局，再用 BFS 求解器
逐辆求出一个可行的驶出顺序**，把这个顺序当作乘客队列的顺序。
求解成功 ⇒ 该关卡在生成时已被证明可解（§6 已知风险 R1 说明了这一步的性能边界）。

**关键设计决策**

| 决策 | 选择 | 放弃 | 理由 |
|------|------|------|------|
| D1 出口位置 | 只有顶部有出口（接客区） | 四边都能出 | 四边出会让"接客区在上方"失去意义，且颜色匹配退化 |
| D2 车辆朝向 | 彩色车必为竖直朝上；障碍车必为横向 | 四种箭头随机分配 | 竖直障碍车会造成**不可逆**阻挡（它永远开不走，被它压住的车永久出局），无法保证可解 |
| D3 驶出判定 | 到达第 0 行即驶出 | 需再点一次才出 | 减少一次无意义点击；同时保证不会有车停留在第 0 行 |
| D4 接客位满时 | 车**开不出去**（被拦停）+ 提示 | 允许驶出后判死局 | 前者可恢复（撤销/挪位），后者是单向门，会制造大量不可挽回的挫败 |
| D5 移动粒度 | 点击 = 滑到底；拖动 = 精确停位 | 只有点击 | 滑到底让谜题可预判；拖动让"停在中途"这个华容道必需的自由得以保留 |
| D6 关卡来源 | 程序生成 + 求解器验证 | 手工设计 100 关 | 无内容团队；程序生成可无限供给，且必然可解 |
| D7 商业化 | 全删 | 广告加位/加道具 | 工程定位是无广告无联网；保留玩法纯粹性 |

## 6. Technical Considerations

**Dependencies**

| 依赖 | 用途 | Owner | Timeline risk |
|------|------|-------|---------------|
| `game.core.GamePlugin/GameRegistry` | 插件注册与大厅渲染 | Eng | Low（已存在且稳定） |
| `data.GameRecordRepository`（Room） | 成绩落库 | Eng | Low（沿用，无需改表） |
| Navigation Component | 新增一个 destination | Eng | Low |
| **BFS 求解器（新建）** | 关卡可解性证明 | Eng | **Med**（唯一的性能不确定项） |

**Known Risks**

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| **R1** 生成耗时（BFS 最坏情况）导致卡顿 | Medium | Medium | 生成放到**后台单线程**，主线程只接收结果；BFS 访问状态数硬上限 6000，布局重试上限 24；仍失败则**降级减少车辆数**再生成 |
| **R2** 求解器找不到解，关卡生成不出来 | Low | High | 重试 + 降车辆数；最坏情况退化为"无障碍车"的保底关卡（必然可解），保证玩家永远有得玩 |
| **R3** 玩家陷入"还能动但已无解"的状态（软锁） | Medium | Low | 无限撤销 + 刷新 + 移除（每关 1 次）三重兜底；不做穷举式"是否仍可解"判定（成本过高），明确登记为已知限制 |
| **R4** 颜色数量对色觉障碍玩家不友好 | Medium | Medium | 颜色**不是唯一编码**：车辆形状（长/短）、箭头方向、接客区色块 + 乘客数量共同编码；色板需过 3:1 非文本对比度 |
| **R5** 8×8 在极小屏（≤ 4.5"）上格子太小 | Low | Medium | 最小格子 26dp + 画布整体居中 + 按比例缩放下限保护 |
| **R6** 成绩字段语义复用造成战绩页文案不精确 | Low | Low | `GameRecord.lines` 复用为"接客数"，战绩页显示"N 行"字样不准确；登记为待办，不在这次动壳层 |

**Open Questions（开发前必须解决）**

- [x] Q1：接客位数量 → **固定 3**（无广告加位，见 D7）
- [x] Q2：是否允许任意颜色插队 → **否，只服务队首**（见 §5）
- [x] Q3：如何保证关卡可解 → **BFS 求解器求顺序**（见 §5）
- [ ] Q4：长期是否需要手工关卡与难度曲线校准 → Owner: PM — Deadline: 上架后 30 天（有数据后再定）
