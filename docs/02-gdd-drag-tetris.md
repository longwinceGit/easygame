## 0. 设计支柱（Design Pillars）

后续每个决策都以这 4 条为标尺。任何与支柱冲突的机制，默认砍掉。

| # | 支柱 | 含义 | 反面 |
|---|------|------|------|
| P1 | **手指即意图** | 玩家想到哪就放到哪，没有中间层（没有左右键、没有软降） | 需要多次点击才能完成一次放置 |
| P2 | **无惩罚的试错** | 放错了不扣分、不消耗、不弹错误弹窗——只是弹回来 | 误操作带来不可逆损失 |
| P3 | **随时可停** | 没有倒计时、没有重力下落，切走再回来局面完全不变 | 时间压力 / 强制在线 |
| P4 | **看得懂为什么输** | 结束局面必须让玩家一眼看出"是我把空间用坏了" | 随机失败、不可归因的失败 |

## 1. 好玩假设（Fun Hypothesis）

> **"在有限空间里做无时间压力的空间规划，其乐趣来自'这一手值不值'的权衡，而不是手速。"**

这是本作成立与否的唯一核心点。如果实现后发现玩家 30 秒内就随便乱放，说明假设不成立——那时应加的不是难度，而是**让权衡显性化**（更好的落点预览、更明显的空间提示）。

## 2. 核心游戏循环

### 即时体验（0–10 秒 / 单次放置）
- **行为**：手指按住托盘方块 → 拖到棋盘上方 → 左右移动观察落点 → 松手
- **反馈**：
  - 拖动瞬间：方块放大 1.08×、抬起阴影、托盘原槽位留空槽（**禀赋效应**：玩家已经"拿在手里"）
  - 移动中：棋盘实时显示**半透明落点幽灵** + 目标列竖向高亮
  - 松手合法：硬降落动画 90ms + 触觉反馈 40ms + 落点行轻微闪白
  - 松手非法：方块 180ms 弹回托盘，无分数变化、无提示弹窗（P2）
- **奖励**：**无直接分数**——放置本身不得分（见机制 7）。即时奖励是硬降落动画 + 触觉反馈 + 落点行闪白，以及"这一手放得整齐"的内在满足感

### 单次会话循环（3–10 分钟 / 一局）
- **目标**：在不把棋盘堵死的前提下，尽可能多地消行、堆高分数
- **紧张感**：**空间**是唯一资源。托盘 3 块用完才补充 → 玩家必须为"接下来 3 块"预留空间（这是本作真正的策略深度来源）
- **决策点**：
  - 这一列放下去会不会留下 1 格宽的洞？
  - 现在消 1 行，还是再垫两块凑 4 行（Tetris）？
  - 要不要为了保住平整度，把一个 I 块横放在次优位置？
- **结局**：托盘中所有剩余方块在**所有列 × 所有旋转**下均无法放置 → 结算卡片（本局分 / 最高分 / 再来一局）

### 长期循环（数天–数周）
- **成长**：无数值成长（P3：不做养成负担）。成长感来自**个人最高分的自我超越**
- **留存钩子**：大厅展示"最高分"，结算卡片显示"距最高分还差 N 分"（**目标梯度效应**：越接近目标动力越强）

## 3. 机制规格书

### 机制 1：拖拽放置（Drag & Drop Placement）

**目的**：把经典俄罗斯方块的"移动 + 旋转 + 硬降"三步操作压缩成一次连续手势（P1）
**玩家幻想**：我直接用手把方块摆到我想摆的地方，棋盘听我的
**输入**：`ACTION_DOWN` 命中托盘方块 → `ACTION_MOVE` → `ACTION_UP`
**输出**：方块 fixed 到棋盘指定列的最底可落行；或回弹到托盘（非法）
**成功判定**：松手后方块出现在手指所在列的可落位置（进入行由手指高度决定）；**未消行时分数不变**
**失败状态**：目标列无处可放 → 方块回弹托盘，棋盘不变，分数不变

**落点计算规则（关键，v1.1 修订）**：
```
left       = clamp(round((fingerX - boardLeft) / cell - shapeWidth / 2), 0, BOARD_W - shapeWidth)
desiredTop = 手指 y 换算出的行（按方块实际绘制的顶部对齐）

row:
  1) top = clamp(desiredTop, 0, BOARD_H - shapeHeight)
  2) 若 canPlace(top) 为假 → 向上顶开，找到第一个能放下的行；找不到则判定非法
  3) 从该行向下探测，取最后一个 canPlace 为真的行（重力吸附）
```

**修订说明（为什么改）**：
v1.0 规定「从 row=0 开始向下探测」，等价于要求方块**从棋盘顶部一路畅通**才能落到底。
实测暴露出这是最影响可玩性的问题：当凹陷的上方被先前放置的方块挡住时，
第二个方块会卡在那块上方、甚至直接判为非法回弹，玩家**无法把方块递进下方的空腔**——
而"填洞"恰恰是这类空间规划游戏最核心的乐趣来源，与设计支柱 P1（手指即意图）直接冲突。

修订后：手指的垂直位置决定**进入高度**，玩家可以把方块"递"进被遮挡的空腔；
同时保留步骤 3 的重力吸附，维持"方块总会落到不能再落"的物理直觉（P4 的可归因性不受影响）。

> 代价：玩家理论上可以把方块放进一个"入口很窄但内部很深"的洞里，
> 这在经典俄罗斯方块（只能从顶部落下）里做不到。这是本作**刻意**的差异——
> 拖拽操作赋予了玩家自由定位的能力，限制它反而会让操作显得失灵。

**边界情况**：
| 情况 | 行为 |
|------|------|
| 手指水平移出棋盘范围 | `left` 被 clamp 到合法区间；只要 clamp 后仍可落子就接受放置 |
| 手指停在托盘区域内松手 | 判定为**点击**（位移 < 8dp）→ 旋转；位移 ≥ 8dp 但仍在托盘内 → 取消拖拽，回弹 |
| 拖拽途中方块被旋转 | 重新计算 `shapeWidth` 与落点（见机制 2） |
| 拖拽中来电 / 切后台 | Fragment `onPause` → 自动暂停，拖拽状态清空，方块回弹 |
| 该列顶部已被占满 | `landingRow < 0` → 幽灵变红，松手回弹 |

**调节杠杆**：`DRAG_THRESHOLD_DP`（点击/拖拽判定阈值）、`DROP_ACCEPT_MARGIN_DP`（棋盘上方多高算有效投放区）、`GHOST_ALPHA`

### 机制 2：旋转（Rotate）

**目的**：给同一方块提供 4 种占位形态，增加空间规划的自由度
**玩家幻想**：这块我换个姿势放
**输入**：在托盘方块上**点击**（`ACTION_UP` 且位移 < 8dp 且时长 < 250ms）
**输出**：该方块 rotation = (rotation + 1) mod 4，顺时针 90°
**成功判定**：方块形状变化，槽位不变，无分数变化
**失败状态**：无失败状态（旋转永远成功；旋转后能否放下由放置阶段判定）

**为什么拖拽中不旋转**（PRD D3）：单指拖拽期间屏幕无法可靠接收第二次点击；双指手势误触率高、学习成本高。代价是玩家"拿起来才发现要转"时要放回托盘——**这个代价被 P2（零惩罚）抵消**。

**边界情况**：
- O 型（2×2）旋转后形状不变 → 视觉上应给出一次极小幅度的"抖动"反馈，让玩家知道系统收到了输入（**不能静默无响应**）`[待测试]`
- I 型（4×4）旋转后宽度从 4 变 1 → 落点列可能需要重新 clamp

**调节杠杆**：`TAP_THRESHOLD_DP = 8`、`TAP_TIMEOUT_MS = 250`

### 机制 3：托盘与补充（Tray & Refill）

**目的**：把"下一块是什么"的随机压力，改成"接下来三块怎么用"的规划压力
**玩家幻想**：我手里有三张牌，我可以决定出牌顺序
**输入**：托盘中某槽位被清空
**输出**：当 3 个槽位**全部为空**时，立即补充 3 个新方块
**成功判定**：放置后若还有剩余方块，游戏继续；全空则立即补 3 个
**失败状态**：补充后若 3 个新方块均无处可放 → 游戏结束（见机制 5）

**为什么要"用完才补"而不是"放一个补一个"**：
- 如果用完一个补一个，托盘永远是满的，玩家可以随意丢弃不喜欢的块 → 规划压力消失
- 只有"必须把这三块都放完"才产生真正的空间权衡（对应好玩假设）

**边界情况**：
- 放置第 3 块后触发补充 → 补充后立刻做 Game Over 判定（顺序不能反：先补，再判）
- 补充时使用 7-bag，保证不会出现"连续 5 个 S/Z"的死亡序列（见机制 6）

**调节杠杆**：`TRAY_SIZE = 3` `[待测试]`（2 太随机，4 太拥挤）

---

### 机制 4：消行（Line Clear）

**目的**：给"保持平整"这一策略以明确回报，构成核心的风险/收益权衡
**玩家幻想**：我把坑填平了，一整行消失了，爽
**输入**：一次放置完成后扫描棋盘
**输出**：所有满行被移除，其上方的行整体下移，计分
**成功判定**：满行消失，上方内容正确下移，分数按公式增加
**失败状态**：无

**边界情况**：
- 一次放置可能同时产生**不连续**的多行满行（例如第 5 行和第 8 行）→ 全部消除，上方按行序压缩
- 消除后新产生的行**不会**再次触发消除（消除是单次的，非递归）→ 避免级联歧义
- 放置的方块本身在满行内 → 正常消除

**调节杠杆**：`CLEAR_FLASH_MS = 160`

---

### 机制 5：结束判定（Game Over）

**目的**：给出可归因的失败（P4）
**玩家幻想**：我知道是我自己把棋盘玩死的
**输入**：每次补充托盘后 / 每次放置后（若托盘仍有块）
**输出**：`state = GAME_OVER`，弹出结算卡片
**成功判定**：托盘中**所有**剩余方块，在**所有列 × 所有 4 个旋转 × 所有行**下都无法放置时才结束

**为什么必须是"所有块 × 所有列 × 所有旋转 × 所有行"**：
只要还有一个块、还有一个角度能塞进去，游戏就没结束。这是唯一能避免"误判死亡"的严谨定义，也让玩家在复盘时无法怪系统。

**v1.1：为什么要加入"所有行"**：
结束判定必须与放置规则保持**同一套可达性语义**。既然 v1.1 允许玩家从任意高度进入，
若结束判定仍只看"从棋盘顶部是否可达"，就会出现"明明还能把方块塞进洞里，游戏却已经判输"。
实现上从棋盘最底部向上找，等价于"存在任意可放置的行"。

**边界情况**：
- 托盘 3 块中 2 块放不下、1 块能放 → **不结束**，玩家必须继续放那 1 块
- 放置最后一块后触发补充，补充的 3 块全都放不下 → 立即结束（玩家会感到"补牌杀了我"，这是可接受的——坑是之前挖的）

### 机制 6：方块生成（7-Bag Randomizer）

**目的**：消除"连续拿到坏块"的不可归因挫败（P4）
**输入**：需要生成新方块时
**输出**：从打乱的 7 种四连块中依次取；取完再打乱新一轮
**成功判定**：任意连续 7 个方块中，7 种类型各出现一次
**失败状态**：无

**为什么不用纯随机**：纯随机下"连续 3 个 S/Z"概率约 1.4%，在低样本量的单局中一旦出现，玩家会归因于"系统针对我"——这是不可归因挫败，直接违反 P4。

**边界情况**：无（bag 内顺序随机，无状态泄漏）

### 机制 7：计分（Scoring）

**目的**：把"消得多、连着消"变成可感知的数字，支撑长期循环的自我超越
**玩家幻想**：我这波四连消赚翻了
**输入**：放置完成 / 消行完成
**输出**：`score` 增加

**公式（v1.2 修订：只有消行才计分）**：
```
放置但没消行 → 得分 = 0，且 combo 归零
消 n 行      → 得分 = (n × LINE_SCORE + MULTI_BONUS[n] + 连击奖励) × level

LINE_SCORE  = 100
MULTI_BONUS = {0, 0, 200, 500, 900}      // 下标 = n
连击奖励     = max(0, combo - 1) × 50 × level
等级         = lines / 10 + 1             // 向下取整，最小 1
combo 规则   = 本次消行则 combo++；未消行则 combo = 0
```

**单次消 n 行的得分表**（level = 1，不含连击）：

| n | 行分 n×100 | 多行奖励 | **合计** | 对比"分 n 次各消 1 行" | **激励倍率** |
|---|---|---|---|---|---|
| 1 | 100 | 0 | **100** | 100 | 1.00× |
| 2 | 200 | +200 | **400** | 200 | 2.00× |
| 3 | 300 | +500 | **800** | 300 | 2.67× |
| 4 | 400 | +900 | **1300** | 400 | 3.25× |

**数值依据（为什么是这些数）**：
| 数值 | 依据 |
|------|------|
| **放置 = 0 分** | 用户明确要求"只有消除才能计分"。设计上也成立：分数是玩家唯一的目标信号，若"堆方块"也能得分，会稀释核心循环、鼓励无脑堆叠。代价是新手前几次放置没有数字反馈——**用消行/得分动画补上即时反馈**（见反馈矩阵），而不是用分数补偿 |
| 行分 100/行 | 作为计分基准单位，所有奖励都以它为参照，便于后续整体缩放 |
| 多行奖励 0/200/500/900 | 让激励倍率随行数递增到 3.25×。倍率要**足够大**才值得玩家为了凑 4 行长期空出一列（这是高风险动作），但**不能更大**——否则非 4 行玩法彻底失去价值，玩家会陷入"干等 I 块"的停滞 |
| × level | 让长局后期分数增长感明显，配合"距最高分还差 N 分"强化目标梯度 |
| combo × 50 × L | 单局内连续消行的奖励，量级约为消 1 行的 1/2，不足以喧宾夺主但可感知 |
| level = lines/10+1 | 一局消 10 行升 1 级，节奏与"3–10 分钟一局"的会话目标匹配 `[待测试]` |

**边界情况**：
- 放置但没消行 → 得分 0，**不播放**得分浮字（避免刷 "+0"），同时打断连击
- 放置即结束（未消行）→ 无得分
- 等级在消行后重算 → 本次消行用**消行前**的等级计分（避免同一次消除里等级跳变导致公式歧义）

**调节杠杆**：全部数值 `[待测试]`

## 4. 经济平衡表（调参表）

```
变量                  | 基础值 | 最小值 | 最大值 | 调参备注
----------------------|--------|--------|--------|------------------------------------------
BOARD_W               | 10     | 8      | 12     | 经典惯例值；<8 策略空间不足
BOARD_H               | 20     | 16     | 24     | 竖屏可见高度决定；小屏可降到 16
TRAY_SIZE             | 3      | 2      | 4      | [待测试] 3 → 2(太随机)/4(太拥挤)
LINE_SCORE            | 100    | 50     | 200    | [待测试] 计分基准单位，整体缩放只改它
MULTI_BONUS[2..4]     |200/500/900 | — | — | [待测试] 激励倍率 2.0/2.67/3.25 是否合适
COMBO_UNIT            | 50     | 25     | 100    | [待测试] 是否值得为连击改变打法
LEVEL_LINES           | 10     | 5      | 20     | [待测试] 与单局时长联动
POPUP_DURATION_MS     | 900    | 600    | 1200   | 手感：太短看不见，太长挡视线
DRAG_THRESHOLD_DP     | 8      | 6      | 12     | 手感：太小易误判为拖拽，太大旋转失效
TAP_TIMEOUT_MS        | 250    | 150    | 400    | 手感：长按后松手不应触发旋转
DROP_ACCEPT_MARGIN_DP | 24     | 8      | 48     | 棋盘上方宽容区，防止手指出界误判取消
CLEAR_FLASH_MS        | 160    | 100    | 250    | [待测试] >250ms 会有"卡顿感"
LAND_ANIM_MS          | 90     | 60     | 150    | 手感：太快没重量感，太慢拖沓
```

**失败标准（测试前先定义）**：
| 现象 | 判定为问题 |
|------|-----------|
| 平均单局 < 60 秒 | 空间压力过大 → 调大 BOARD_H 或减小 TRAY_SIZE |
| 平均单局 > 15 分钟 | 无压力 → 减小 BOARD_H 或增大 TRAY_SIZE |
| 拖拽放置成功率 < 90% | 投放区太严格 → 增大 DROP_ACCEPT_MARGIN_DP |
| 玩家从不凑 4 行 | 超线性不够 → 提高 CLEAR_BASE[4] |

## 5. 新手引导（前 15 秒上手路径）

- [x] **核心操作在 30 秒内引入** —— 首屏托盘第一个方块上有一枚呼吸动画的"↑"箭头 + 文案「按住我，拖到棋盘上」
- [x] **第一次成功是保证的** —— 空棋盘，任何放置都合法，不可能失败
- [x] **低压力环境引入新机制** —— 「点击方块可旋转」在玩家**第一次把方块拖回托盘**时（即他明显卡住了）才浮层提示，而不是一开局就弹
- [x] **至少一个机制靠探索发现** —— 不主动告知"三个用完才补充"；玩家放完第三个时自然看到补牌动画，自己领悟（这正好是策略深度的来源）
- [x] **首次会话结束留有钩子** —— 结算卡片显示「最高分 X，本局 Y，还差 Z」

## 7. 无障碍与色觉友好

- 7 种方块**形状本身各不相同**（I/O/T/S/Z/J/L），形状是第一识别通道，颜色是第二通道 → 单一色觉障碍不会导致无法游玩
- 每种方块额外绘制内缩 22% 的浅色内框 → 在去色（灰度）场景下仍可区分方块边界
- 棋盘格子线使用 `outline_variant`，与方块填充色对比度 ≥ 3:1

## 📌 交接给「软件架构师」的输入

1. **引擎必须是纯 Java、零 Android 依赖**：`Board` / `Tetromino` / `TetrisEngine` 不得 import 任何 `android.*`（这样才能 JVM 单测，且换渲染层时逻辑不动）
2. **引擎需要暴露的接口**（供 ViewModel 与 View 调用）：
   - `int[][] getCells()` — 渲染棋盘
   - `Tetromino[] getTray()` — 渲染托盘（已用槽位为 null）
   - `int landingRow(int slot, int left)` — 幽灵预览
   - `void rotate(int slot)` — 点击旋转
   - `PlaceResult place(int slot, int left)` — 放置，返回 `{success, clearedRows[], gained, combo, gameOver}`
   - `boolean canPlaceAnywhere(int slot)` — 结束判定
   - `start() / pause() / resume() / restart()`
   - `score / lines / level / state`
3. **状态机**：`READY → RUNNING ⇄ PAUSED → GAME_OVER → (restart) READY`
4. **必须可注入随机种子**：`new TetrisEngine(long seed)`，用于单测复现
5. 棋盘尺寸 10×20，托盘 3 格，7-bag 生成器
6. 消行动画需要引擎返回 `clearedRows[]`（行索引），由 View 播放 160ms 闪烁
