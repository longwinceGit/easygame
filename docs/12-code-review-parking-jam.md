## 2. 已修复的重要项（测试驱动）

### 2-1 🔴 驶出判定的方向符号写反了（fuzz 抓到）

`move()` 原来写的是 `v.row + delta == 0` 判驶出。但 ↑ 的 `dRow = -1`，
前进 `delta` 格后行号是 `row - delta`。结果：车开到第 0 行**却不驶出**，
永远停在场地上。离线 fuzz 的不变量"不得有车停留在第 0 行"当场爆出 776 条违规。

**修复**：先算 `newRow = v.row + v.direction.dRow * delta`，再判 `newRow == 0`。
`canExit()` 同步修正，并补上 `canAdmit` 参与判断（否则车贴边时 `boundary==0` 会被误判成"可驶出"）。

**教训**：凡是"带符号的方向量"参与比较，都用 `dRow/dCol` 统一推导，不要手写符号。

### 2-2 🔴 BFS 与真实引擎的"驶出"语义不一致（完备搜索抓到）

第一版求解器允许**非目标**车开到边界并在棋盘上停住（BFS 里"到边界"= 目标达成）。
但真实引擎里"到达边界"等价于**驶出**，会消耗一个接客位。
结果：约 10% 的关卡在真实引擎里无解——BFS 求出的解复现不了。

**修复**：BFS 中非目标车最多开到离边界一格（由拖动实现），
使 BFS 可达状态成为真实游戏的**子集**。"BFS 能解 ⇒ 一定能解"这条推理这才真正成立。

**教训**：ADR-008 原文声称的"保守性"在第一版里是**错的**，而且是错的还没被发现——
因为当时没有任何可执行验证。这条教训直接催生了 §3 的离线验证。

### 2-3 🟡 「移除」会制造必然软锁（设计评审抓到）

「移除」允许拿掉任意一辆车，但那辆车的乘客还在队列里等——
它们永远等不到车，关卡必然无法通关。

**修复**：移除车辆时同步把该颜色的 `capacity` 位乘客一并移出队列（本关总人数同步扣减），
守恒量 `队列人数 + 已接客 == 总人数` 得以维持。

### 2-4 🟡 驶出动画与接客区重复绘制（自查抓到）

车辆驶出后立刻进入接客区列表，接客区会把车画在车位里，
同时驶出动画又在画同一辆车 → 一个车影分身。

**修复**：接客区绘制时跳过正处于驶出动画中的那辆车；动画结束的那一帧先 `clearExit()` 再画。

## 3. 本次交付里最值得肯定的部分

1. **离线验证直接改变了实现**。`ParkingLevelGenerator` / `ParkingEngine` 是纯 Java，
   用 `javac` 编出来就能跑。三个缺陷里有两个是它抓出来的。
   验证结论：**240 关中 239 关被完备 BFS 证明可解**，剩下 1 关用公开 API 重放 7 步到 SOLVED
   （是验证器自身不完备，非产品缺陷）；fuzz 数百步**零不变量违规**。
2. `ADR-009` 全量快照撤销是正确选择——接客/排序/移除都会改 5 处以上状态，
   逆向操作必然漏。实测撤销在排序、移除、接客链上全部正确回滚。
3. `Level` 做成不可变值对象，让"后台生成 → 主线程套用"这条跨线程边界没有共享可变状态。
4. 引擎的只读查询用 `vehicleAt(index)` 而不是每次返回新集合，`onDraw` 内零分配成立。
5. 命中测试先做一次逆旋转再比矩形，把"倾斜棋盘"的全部复杂度压在一个方法里。

## 4. 登记未修（不阻塞合入）

### 4-1 🟡 「排序」可能把可解关卡排成不可解

重排队列后不保证仍存在解法。缓解：排序会入撤销栈，一步可退；「刷新」免费。
**真正的修法**是给引擎加"给定顺序的可解性校验"，成本是一次 BFS，放在排序前执行。
登记为 V1.2。

### 4-2 🟡 生成最坏耗时未在低端机实测

后台线程跑，平均 39ms/关（JVM 实测），但最坏路径（24 次重试 × 7 次 BFS）没有真机数据。
PRD §7 已写回滚准则（P95 > 800ms 则退化为固定种子关卡）。

### 4-3 🔵 一处色值字面量

`ParkingRenderer` 早期版本曾用 `0xFFFFFFFF` 画计数牌文字，已改为 `game_parking_sign_text` 资源。
复核时需确认没有回归；`ColorUtils.blendARGB(color, 0xFFFFFFFF/0xFF000000, …)` 属于**混色运算的参数**而非色板取值，豁免。

### 4-4 🔵 战绩页字段语义复用

`GameRecord.lines` 被挪车消消消复用为"接客数"，战绩页文案仍显示"N 行"。
改法是让 `GameDescriptor` 提供一个格式化器，但那要动壳层契约，超出本次"新增模块"的范围。

## 8. 难度调优（本轮反馈：关卡太简单 / 图标太大）

用户三点反馈：①关卡太简单 ②随关卡增加车辆与乘客要变多 ③棋盘格子太少、图标太大。改动与实测：

| 项 | 改前 | 改后 | 实测 |
|----|------|------|------|
| 棋盘 | 6×6 | **8×8** | 旋转后外接盒约 10.4 格，小屏格子 ~26–31dp（图标更小） |
| 车辆数上限 | 7 | **10**（`clamp(4+关, 5, 10)` → L1=5…L6+=10） | 车 5→10、乘客 12→24 |
| 难度门槛 | 无 | `minSolutionMoves = 车辆数 + min(3, 1+关/4)` | 拒绝"每辆车都能直接开走"的过简布局 |
| 生成耗时 | 39ms | L1≈7ms … L8≈0.5s（最坏 2.2s） | 后台线程 + 加载中提示，可接受 |

**为什么车辆上限停在 10 而不是 12**：8×8 + 12 车时单次关卡的 BFS 求解最坏冲到 ~10s、平均 ~3s，
超出"后台生成不应卡 UI"的底线；压到 10 车后最坏回落到 ~2.2s，且 0 关回退到应急废局。
（已登记为 V1.2 的优化点：把生成器 BFS 从"全量克隆状态"改为"原地 undo + 记忆化"，可在不涨耗时的情况下把上限推回 12。）

**可解性证据**：本轮新增「完整 DFS 求解器」复验。高关卡因状态空间超限出现假阴性，但
`Diag` 实测**所有关卡失败回退数 = 0**——即生成器对每个关卡都成功求出了完整驶出顺序（构造式可解），
从不在抽不出解时掉到 2 车应急局。构造式证明独立于求解器，结论可靠。
